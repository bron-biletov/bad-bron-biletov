В этом проекте нужно с помощью Kilo Code создать робота "Bron Biletov", который сможет бронировать ж/д билеты на сайте https://pass.rw.by/ru/

Речь идёт о таких билетах, которые сложно забронировать самостоятельно, потому что они продаются на популярные рейсы и их быстро раскупают. Но периодически в продажу возвращаются те билеты, от которых отказались.

Робот должен запросить у пользователя данные его учётной записи (логин и пароль), рейс (поезд и время), а также данные пассажира (ФИО, данные документа удостоверяющего личность и номер телефона).

На основе этих данных он должен войти в систему бронирования на сайте https://pass.rw.by/ru/ , найти нужный рейс и проверять с некоторой периодичностью, не появился ли хотя бы один доступный билет.

Как только билет появится, он должен его оперативно забронировать, пока этого не сделал какой-то другой покупатель.

Когда билет куплен, робот должен уведомить об этом пользователя.

## Реализация

Робот реализован на Python с использованием Playwright (управление реальным
браузером Chromium). Исходный код находится в `src/bron_biletov/`:

- `config.py`, `models.py` — загрузка и валидация настроек из `config.yaml`;
- `browser.py` — запуск браузера и сохранение сессии (куки) между запусками;
- `rw_site.py` — вход на pass.rw.by, поиск рейса, попытка бронирования;
- `poller.py` — цикл периодической проверки наличия мест со случайным
  интервалом (защита от предсказуемой нагрузки на сайт);
- `notifier.py` — звуковое уведомление об успешном бронировании;
- `__main__.py` — точка входа CLI.

### Установка

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python -m playwright install chromium
```

### Настройка

1. Скопируйте `config.example.yaml` в `config.yaml`.
2. Заполните в `config.yaml`: логин/пароль от личного кабинета pass.rw.by
   (или задайте переменные окружения `RW_LOGIN` / `RW_PASSWORD`, они имеют
   приоритет), данные пассажира и параметры искомого рейса (станции, дата,
   при возможности — номер поезда и время отправления).
3. `config.yaml` уже добавлен в `.gitignore` — он не попадёт в git.

### Запуск

```powershell
python -m bron_biletov --config config.yaml
```

Первый запуск рекомендуется делать с открытым окном браузера
(`browser.headless: false` в конфиге, либо флаг `--headed`), чтобы убедиться,
что вход, поиск и бронирование проходят корректно на актуальной версии сайта.
Флаг `--once` выполняет одну проверку и завершает работу — удобно для отладки.

### Важные замечания

Логика в `rw_site.py` проверена вживую (headless-прогоны против настоящего
pass.rw.by, без реального аккаунта) для следующих шагов — они основаны на
подтверждённой фактической разметке, а не на предположениях:

- баннер cookie-согласия и его закрытие;
- форма входа (`input[name="login"]`, `input[name="password"]`, кнопка
  `input[type=submit][value="Войти"]`) и распознавание ошибки логина
  (блок `.danger.standalone`, например текст «Пользователь не найден»);
- определение статуса авторизации;
- построение URL поиска рейса и разбор таблицы результатов
  (`div.sch-table__row-wrap`, класс `w_places` = места есть, кнопка
  «ВЫБРАТЬ МЕСТА»; без `w_places` и с текстом «Мест нет» = мест нет);
- выбор типа вагона и конкретного вагона на странице `/ru/order/places/`
  (после этого шага сайт сам назначает номер места — выбирать место на
  схеме вручную не требуется);
- номер поезда берётся из параметра `train=` в ссылке строки результатов
  (надёжнее регулярки по тексту — не путается на составных маршрутах и
  4-значных номерах пригородных поездов);
- любая неожиданная блокирующая Bootstrap-модалка (например «Результаты
  поиска могли устареть» или «Соединение с системой продажи проездных
  документов было прекращено из-за длительного простоя») закрывается
  автоматически перед каждым важным действием (`dismiss_known_overlays` →
  `dismiss_unexpected_modals`), причём без знания конкретного `id` модалки —
  закрывается любая видимая `.modal.in`, кроме формы входа;
- на странице выбора вагона убраны избыточные ожидания `networkidle`
  (страница держит фоновое соединение с backend, из-за которого сеть может
  не "затихать" по 10-15 секунд на каждом шаге без всякой причины — именно
  накопление таких ожиданий, вероятно, и провоцирует показ модалки о
  простое), заменены на точечное ожидание нужных элементов;
- клики по типу вагона и по вагону в аккордеоне используют `_click_robust` —
  если элемент перекрыт липкой нижней панелью с ценой (`.carriage-cost.fixed`)
  и обычный клик виснет с бесконечными попытками скролла (внешне похоже на
  хаотичное скроллирование страницы вверх-вниз), делается повторная попытка
  через `force=True`; если тип вагона у поезда всего один и уже выбран по
  умолчанию (класс `active`), клик по нему не выполняется вовсе.

**Про `route.train_number` и `route.departure_time` в конфиге:** оба
значения нужно писать в кавычках. Без кавычек YAML разбирает `19:38` как
число (1178 в шестидесятеричной записи), а не как строку "19:38" — теперь
`config.py` явно проверяет это и остановится с понятной ошибкой вместо
того, чтобы молча искать несуществующий рейс.

Форма пассажира на `/ru/order/passengers/` тоже откалибрована вживую (по
дампу реальной страницы под настоящим аккаунтом): поля используют реальные
`name`-атрибуты (`last_name_1`, `first_name_1`, `middle_name_1`,
`document_number_1`), тип документа — обычный `<select name="document_type_1">`
с двухбуквенными кодами БЖД (маппинг человекочитаемых значений из
`config.yaml`, например `id_card` → `ИК`, — в `DOCUMENT_TYPE_VALUE_MAP`).
На этой странице **нет поля телефона** — оно относится к отдельному
виджету поддержки на той же странице, а не к пассажиру, поэтому
`passenger.phone` сейчас не используется этим шагом. Кнопка «Оформить
заказ» по умолчанию `disabled` и включается сайтом только после отметки
чекбокса согласия с правилами (`name="agreement"`) — бот отмечает его
автоматически и дожидается разблокировки кнопки перед кликом.

Если на реальном заказе для вашего типа документа сайт запросит
дополнительные поля (дата рождения, гражданство, пол — они присутствуют в
разметке как скрытые/опциональные для некоторых типов документов), их
понадобится добавить отдельно: сейчас код заполняет только ФИО, тип и
номер документа.

Следующий неоткалиброванный шаг — экран после «Оформить заказ» (`Корзина
билетов`), где, вероятно, и указывается телефон и итоговое подтверждение
брони. Пока `book_train()` определяет успех эвристически (по отсутствию
слов «ошибка»/«не удалось» на странице) — при первом реальном дохождении
до этого шага стоит уточнить более точный признак успеха.

Дополнительно:

- Робот доводит процесс до создания брони/заказа и уведомляет пользователя
  звуковым сигналом и записью в лог; финальную оплату (ввод данных карты)
  автоматизация не выполняет — её нужно завершить вручную в личном кабинете
  в течение отведённого на бронь времени.
- Интервал опроса по умолчанию — случайная пауза 15–30 секунд между
  проверками, чтобы не создавать чрезмерную нагрузку на сайт; при
  нескольких ошибках подряд робот увеличивает паузу (`error_backoff_seconds`).
